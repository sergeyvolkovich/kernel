# rust-l4: песочница GTCB — атрибуты, права, спавн (v0.9–v0.13)

Домен rust-l4 (GTCB) — это cspace + адресное пространство + АТРИБУТЫ
защиты в TCB. Песочница — набор rlimit-стилем пределов, назначаемых
держателем TaskTCB-права на домен (родитель — порождённому), плюс
отсутствие capability, которых домену не выдали. Семантика изменения —
«трещотка»: пределы можно только УЖЕСТОЧАТЬ, поэтому даже задача,
владеющая TaskTCB на саму себя, не может расширить собственную
песочницу.

## 1. Модель GTCB

GTCB (Global Task Control Block) — задача-домен L4: protection domain,
владеющий cspace (пространство capability-хендлов) и адресным
пространством. Потоки — единица планирования — живут внутри домена и
разделяют его cspace и память. Идентификаторы TaskId/ThreadId — единое
пространство имён UUID (как chief-IDs L4-Fiasco).

Атрибуты защиты — часть TCB домена (`TaskObj` в `TcbManager`):

- **`TaskLimits`** — верхние границы потребления (rlimit-стиль;
  `usize::MAX` = без предела; дефолт UNLIMITED — доверенные службы
  ядра);
- **`TaskUsage`** — текущее потребление, ведётся ядром в точках
  зарядки (заряд ДО операции, атомарный откат при отказе подсистемы);
- ленивые счётчики `live_threads` (v0.10): инкремент в
  THREAD_CREATE, декремент в Dead-переходе потока — проверка
  max_threads и подсчёт — O(1), без обхода реестра.

Назначение пределов — syscall TASK_SET_LIMITS (0x1D) по праву TaskTCB
на ЦЕЛЬ; чтение снапшота пределов+usage — TASK_LIMITS_INFO (0x1E).
Ключевые свойства модели:

- **Трещотка**: `TaskLimits::tighten` — минимум по числовым полям,
  логическое И по may_spawn; итог никогда не слабее текущего.
- **Атомарность рождения**: лимиты применяются ДО первого потока
  ребёнка — «окно без лимитов» у нового домена невозможно (v0.9).
- **Отсутствие capability — часть песочницы**: дети не получают
  IommuAdmin, TaskTCB на чужие домены, DeviceReference; права
  появляются только передачей от родителя (CAP_MINT — копия,
  CAP_SEND — переезд хендла).

## 2. TaskLimits: пределы

| Поле | Что режет (errno) |
|------|-------------------|
| `max_pages` | MEM_ALLOC + входящие окна map/transfer/SHM (`-122` EDQUOT) |
| `max_threads` | THREAD_CREATE, главный поток считается (`-122`) |
| `max_endpoints` | живые Gate-capability (EP_CREATE; учёт по cspace — CAP_DELETE/REVOKE честны) (`-122`) |
| `max_shm` | SHM_CREATE (`-122`) |
| `max_caps` | живые хендлы cspace: CAP_MINT/CAP_SEND/EP_CREATE (`-122`) |
| `max_prio` | потолок THREAD_SET_PRIO/приоритета домена (0..=255) (`-122`) |
| `may_spawn` | право творца: TASK_CREATE/TASK_SPAWN_IMAGE (`-1` EPERM) |
| `cpu_quota` | тиков планировщика за период (v0.10; учёт v0.13 — циклами TSC) — [cpu-quotas.md](cpu-quotas.md) |

ABI TASK_SET_LIMITS (упаковка слов — `syscall/nums.rs`):

```
arg1 = хендл TaskTCB цели
arg2 = max_pages
arg3 = max_threads | (max_endpoints << 32)
arg4 = max_shm    | (max_caps << 32)
arg5 = max_prio (u8) | (may_spawn ? 0x100 : 0) | (cpu_quota << 16)
      cpu_quota: биты 63:16 = 0 — «не трогать» (наследие v0.9: старые
      вызовы не замораживают домен), все единицы — «без лимита»,
      1.. — квота в тиках за период
```

Ошибки пределов — новый errno `QuotaExceeded` (-122, EDQUOT);
SpawnDenied — EPERM. Проверка предела происходит ДО расхода
(зарядка → операция → откат при отказе) — домен не может «проесть»
кусок чужой квоты частично успешной операцией.

## 3. TaskUsage: учёт

```rust
pub struct TaskUsage {
    pub pages: usize,             // MEM_ALLOC + входящие окна
    pub shm: usize,               // живые SHM-регионы
    pub cpu_used: usize,          // тики текущего периода (floor от циклов)
    pub cpu_used_cycles: u64,     // первичный точный счётчик (v0.13)
    pub cpu_throttled: bool,     // домен за пределом квоты сейчас
    pub cpu_throttle_events: usize, // сколько раз входил за предел
}
```

Счётчики ведутся в точках расхода с атомарным откатом: если подсистема
отказала после зарядки (страничная таблица, дескриптор), заряд
возвращается. Категория «endpoints» не хранится числом — вычисляется по
живым Gate-capability (счётчик разошёлся бы с реальностью при отзыве).
CPU-учёт — производный от планировщика (заряд на концах отрезков
исполнения, см. [cpu-quotas.md](cpu-quotas.md)).

TASK_LIMITS_INFO — слова по индексу: 0 max_pages, 1 usage.pages,
2 usage.shm, 3 max_threads|(max_endpoints<<32), 4 max_shm|(max_caps<<32),
5 max_prio|(may_spawn?0x100:0), 6 cpu_quota, 7 cpu_used (тики текущего
периода), 8 cpu_throttle_events|(cpu_throttled?1<<32:0).

## 4. Харднинг прав (v0.9)

Закрытые дыры v0.8 — каждое правило права теперь проверяется
capability-слоем:

| Операция | Право (было до v0.9) |
|----------|----------------------|
| IOMMU-группа 0x80 (ENUM/ATTACH/MAP/UNMAP/DETACH/IRQ_*) | capability **IommuAdmin** (kind=5; выдаёт kinit доверенным — init; дети не получают и не передают). Было: ЛЮБОЙ домен |
| MEM_TRANSFER (flexpage-окно в чужой домен) | TaskTCB на ПОЛУЧАТЕЛЯ. Было: знание TaskId |
| CAP_MINT/CAP_SEND в чужой cspace | TaskTCB на получателя + предел max_caps получателя (флуд чужого cspace = DoS) |
| THREAD_TERMINATE/DESTROY/SET_PRIO | TaskTCB домена цели ИЛИ свой домен + потолок max_prio (эскалация 255 = захват CPU) |
| SHM (SETUP_RING/BIND_DOORBELL/MAP/DESTROY/RING_DOORBELL) | только владелец региона (угаданный ShmId более не рушит чужие кадры) |
| TASK_CREATE/TASK_SPAWN_IMAGE | право творца гасится may_spawn (песочница не плодит домены-«побеги» с чистыми лимитами) |
| MEM_MAP_AT (спавн-протокол) | TaskTCB на цель + зарядка квоты ЦЕЛИ |

Багфикс IPC_RECV (0x33): прямая встреча (неблокирующий путь)
выбрасывала сообщение после чтения слова 0 — слова 1.. были недоступны
через IPC_MSG_WORD; все пути теперь заполняют mailbox.

## 5. Спавн доменов

Философия: **ядро не знает про ELF и не копирует образы в рантайме**.
Сискол спавна принимает УЖЕ залинкованный образ, ПОЛНОСТЬЮ
подготовленный родителем: ядро получает ТОЛЬКО указатели на память
родителя и мапит готовые кадры в новое пространство (external-окна,
zero-copy, без единой пересылки данных).

**TASK_SPAWN_IMAGE (0x1F)** — основной путь. Родитель обязан к моменту
вызова: (1) разобрать ELF64 (PT_LOAD, e_entry) — крейт `pie` (для PIE)
или свой парсер; (2) выделить себе регионы MEM_ALLOC под сегменты,
стек, argv-блок и дескриптор; (3) скопировать байты сегментов (BSS —
нулём: кадры из пула несут мусор); (4) собрать дескриптор спавна в
СВОЕЙ памяти. Дескриптор (LE, выравнивание 8; полный формат —
`syscall/nums.rs` и [apps-and-servers.md §10](apps-and-servers.md)):

```
+0x00 u64 entry         линк-точка входа ребёнка
+0x08 u64 stack_top     вершина стека (RSP первого контекста)
+0x10 u64 thread_id_lo/hi   ThreadId главного потока
+0x20 u32 n_segments   1..=16 (образ + стек)
+0x24 u32 argv_pages   0 = без argv
+0x28 u64 argv_src/dst/bytes  argv-блок у родителя / у ребёнка
+0x40 u64 argc         argc стартового IPC
+0x48 u64 limits[0..3] max_pages; threads|endpoints; shm|caps; prio|may_spawn
+0x68 u8  priority     приоритет домена/потока
+0x6C u32 cpu_quota    квота CPU ребёнка (v0.10): 0/0xFFFFFFFF = без
                       лимита, 1..=0xFFFFFFFE = квота — ДО первого потока
+0x70 сегменты (32 байта): src(родитель), dst(ребёнок, 4K-выровнен),
     pages, flags (MMAPMemoryFlags: RO=1 W=2 X=4, W^X обязателен)
```

Порядок в ядре: домен → пространство (SpaceFactory) → ЛИМИТЫ (до
первого потока!) → грант TaskTCB(ребёнка) родителю → сегменты (зарядка
квоты ребёнка + map_external_at) → argv → главный поток → стартовое
IPC `[argc, argv_dst, argv_bytes]` в очередь потока (как kinit для
init). Отказ любого шага — полный откат домена (Dead-каскад →
destroy_space → TCB destroy): у ребёнка нет «частично собранного»
состояния, у родителя нет утечек стейджинга (возврат страниц — на его
совести, MEM_FREE).

Возврат — хендл TaskTCB(ребёнка) в cspace родителя: лимиты, потоки,
kill, TASK_SET_EXIT_EP.

**Низкоуровневый путь** (полный контроль): TASK_CREATE (домен +
пространство + грант родителю) → MEM_MAP_AT (0x55; map_fixed своих
кадров по линк-адресам ребёнка, заряд квоты цели) → THREAD_CREATE →
IPC_SEND_THREAD (стартовое IPC) → TASK_SET_LIMITS. Это тот же
контракт, из которого собран TASK_SPAWN_IMAGE.

## 6. PIE-образы (v0.11)

До v0.11 спавнились только статические ET_EXEC по фиксированным
адресам. v0.11 решает открытый пункт «динамический релок» — в
соответствии с философией: **загрузчик живёт в юзерспейсе** (крейт
`pie`, без единой аллокации):

- `Plan::parse(blob)` — разбор ELF64: e_entry, план PT_LOAD-сегментов
  (страницы, флаги W^X), таблица RELA-релокаций. Только
  **R_X86_64_RELATIVE** — образы с символным релокированием
  freestanding-домен не поддерживает, парсер отказывает (fail-closed).
  ET_EXEC принимается как `StaticFixed` (легаси v0.9) — один парсер
  для обоих.
- `Plan::apply_rela(base, store)` — накат релокаций под выбранную
  базу: `*(base + r_offset) = base + r_addend` через колбэк записи в
  собственную память родителя.
- Родитель выбирает базу (например 0x40000000 или 0x50000000),
  копирует образ в стейджинг, применяет релоки, собирает дескриптор —
  и спавнит обычным TASK_SPAWN_IMAGE. Два домена из ОДНОГО образа на
  разных базах — ASLR-класс изоляции между доменами.

Сборка PIE-приложения: rust-lld `--pie` + `-C relocation-model=pic`
(build.sh делает это за rogue: `ROGUE_PIE=1` по умолчанию, контроль
`readelf -h` — ET_DYN обязателен; `ROGUE_PIE=` — легаси-ET_EXEC-режим
отладки). Демо-верификация в init S4: один образ спавнится на ДВУХ
базах, ребёнок возвращает статический указатель (PIE_PTR), init
сверяет ожидаемое значение — накат релокаций проверяется контрольным
readback на живом домене.

Ограничения контракта: до 16 PT_LOAD-сегментов, до 256
R_X86_64_RELATIVE-релокаций, до 64 записей .dynamic (константы крейта;
образы демо — единицы, freestanding-PIE без символных ссылок даёт
десятки).

## 7. Смерть домена

Контракт смерти (v0.9): TASK_EXIT/kill/фолт → `Glue::reap_thread`:

```
revoke_all(cspace домена)   → capability гасятся с производными
SHM-регионы                 → кадры в пул
TCB destroy                 → реестр задач чист
destroy_space               → фасад под владением менеджера памяти:
                              owned-кадры — пулу, external-окна
                              (стейджинг родителя) — остаются
                              источнику (L4 pager-модель)
```

Уведомление родителя — exit-endpoint: TASK_SET_EXIT_EP(gate)
регистрирует endpoint ДОБРОВОЛЬНО; ядро доставляет ExitPayload:
tag 1 = **Exit** (w3 = код, w4 = cpu_used, w5 = cpu_throttle_events —
CPU-вердикт песочницы без гонок с reaper'ом), 2 = **Exception**
(фолт; снимок регистров + fault-слова), 3 = **Killed** (кем). Мёртвый
домен исчезает из реестра — TASK_LIMITS_INFO по нему отвечает NotFound,
поэтому CPU-итог везёт сам payload.

Каскад смерти домена гасит его потоки (state → Dead через
диспетчер), отпускает claims устройств, снимает IRQ-привязки
(IrqRouter), паркует внешние линии IOAPIC.

## 8. Аудит и операторская картина

Каждая блокировка песочницы печатает `[kernel: sandbox] …` в консоль
отладки: квоты (pages/threads/endpoints/shm/caps/prio), права
(угаданные хендлы, отсутствующая IommuAdmin, owner-гейты SHM),
троттлинг CPU (`cpu quota: domain … throttled (charged N cycles, limit
K ticks per period)`). Оператор видит картину атаки вживую.

Демо-прогон «rogue» (init S4, воспроизводится во всех трёх
конфигурациях QEMU): ребёнок с лимитами (max_pages 61, threads 4,
endpoints 3, shm 2, caps 8, prio 100, may_spawn=0, cpu_quota=3)
атакует: флуд потоков (3 потока, 4-й −122), эскалация приоритета,
kill родителя по угаданному хендлу, спавн своего домена, захват
IOMMU, SHM-флуд, разрушение SHM родителя, проталкивание капов в
cspace родителя, флуд памяти — 9 нарушений блокированы, вердикт
`sandbox HELD` + `cpu quota HELD`, честный TASK_EXIT(0x5A): квота
дисциплинирует, но не душит протокол ping-pong.
